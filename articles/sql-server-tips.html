SQL Server Tips

Catatan praktis dari pengalaman bekerja dengan SQL Server

SQL Server adalah salah satu teknologi database yang sudah lama saya gunakan dalam pekerjaan sehari-hari.

Selama bertahun-tahun bekerja dengan aplikasi bisnis, ERP, dan berbagai aplikasi internal perusahaan, saya menemukan bahwa masalah database sering kali bukan hanya tentang bagaimana membuat query yang benar.

Query bisa saja menghasilkan data yang benar, tetapi belum tentu memiliki performa yang baik.

Di artikel ini saya ingin mengumpulkan beberapa tips dan pengalaman praktis yang sering saya gunakan ketika bekerja dengan SQL Server.

1. Jangan Langsung Menyalahkan SQL Server

Ketika aplikasi terasa lambat, sering kali database langsung menjadi tersangka pertama.

Padahal masalah bisa berasal dari banyak hal:

  • Query yang tidak optimal
  • Index yang tidak sesuai
  • Jumlah data yang terlalu besar
  • Blocking
  • Deadlock
  • Network
  • Program aplikasi
  • Hardware server

Karena itu langkah pertama bukan langsung mengubah query. Cari tahu terlebih dahulu di mana masalah sebenarnya terjadi.

2. Gunakan SELECT Hanya untuk Kolom yang Dibutuhkan

Hindari kebiasaan menggunakan: 

SELECT *
FROM Employee

jika sebenarnya hanya membutuhkan beberapa kolom. 

SELECT EmpID, EmpName, Department
FROM Employee

Mengambil kolom yang diperlukan membuat query lebih jelas dan dapat mengurangi data yang harus diproses serta dikirim melalui network.

3. WHERE Sangat Penting

Salah satu kesalahan yang cukup sering ditemukan adalah mengambil seluruh data kemudian melakukan filtering di aplikasi.

Lebih baik filtering dilakukan langsung di SQL Server. 

SELECT EmpID, EmpName
FROM Employee
WHERE IsActive = 1

Database engine dapat melakukan filtering sebelum data dikirim ke aplikasi.

4. Hati-Hati dengan LIKE

Query seperti berikut: 

SELECT *
FROM Employee
WHERE EmpName LIKE '%Yusep%'

dapat menjadi berat jika jumlah data sangat besar, terutama ketika kolom tersebut tidak dapat menggunakan index secara efektif.

Jika kebutuhan pencarian memungkinkan, kondisi seperti: 

WHERE EmpName LIKE 'Yusep%'

biasanya lebih bersahabat terhadap penggunaan index dibandingkan pencarian dengan wildcard di awal.

5. Gunakan Index dengan Bijak

Index dapat membuat query menjadi jauh lebih cepat. Tetapi terlalu banyak index juga bukan solusi.

Setiap INSERT, UPDATE, dan DELETE harus memperbarui index yang berkaitan.

Karena itu index harus dibuat berdasarkan pola penggunaan query, bukan sekadar menambahkan index sebanyak mungkin. 

CREATE INDEX IX_Employee_EmpID
ON Employee(EmpID)

6. Jangan Abaikan Execution Plan

Kalau sebuah query terasa lambat, jangan hanya membaca query-nya. Lihat juga execution plan.

Execution plan dapat membantu mengetahui bagaimana SQL Server menjalankan query tersebut.

Dari execution plan kita dapat melihat operasi seperti:

  • Index Seek
  • Index Scan
  • Table Scan
  • Key Lookup
  • Sort
  • Hash Match
  • Nested Loops

Dari sini kita dapat mulai mencari bagian query yang membutuhkan perhatian.

7. Hati-Hati dengan Function pada Kolom

Salah satu pola yang sering saya temui adalah penggunaan function langsung pada kolom yang digunakan untuk filtering. 

WHERE YEAR(TglTransaksi) = 2026

Untuk data yang besar, pendekatan range tanggal sering lebih baik. 

WHERE TglTransaksi >= '20260101'
  AND TglTransaksi <  '20270101'

Selain lebih mudah dibaca, pendekatan ini juga dapat memberikan kesempatan yang lebih baik bagi SQL Server untuk menggunakan index pada kolom tanggal.

8. Gunakan Parameter, Jangan Membentuk SQL Secara Sembarangan

Dalam aplikasi seperti VB6, C#, atau aplikasi lainnya, query sering dibentuk menggunakan concatenation string. 

SELECT *
FROM Employee
WHERE EmpID = '...'

Untuk aplikasi production, parameterized query lebih aman dan lebih baik daripada memasukkan input user langsung ke dalam SQL.

Selain masalah keamanan seperti SQL Injection, penggunaan parameter juga membantu menjaga query tetap terstruktur.

9. Gunakan Stored Procedure Jika Memang Dibutuhkan

Stored Procedure sangat berguna untuk proses bisnis yang kompleks dan sering digunakan. 

CREATE PROCEDURE sp_GetEmployee
    @EmpID VARCHAR(20)
AS
BEGIN

    SELECT
        EmpID,
        EmpName,
        Department
    FROM Employee
    WHERE EmpID = @EmpID

END

Namun jangan membuat semua hal menjadi Stored Procedure hanya karena kebiasaan.

Pilih pendekatan berdasarkan kebutuhan aplikasi, maintenance, keamanan, dan performa.

10. COUNT(*) Tidak Selalu Masalah

Banyak developer menghindari COUNT(*) karena menganggap selalu berat. 

SELECT COUNT(*)
FROM Employee

Sebenarnya performa COUNT bergantung pada kondisi data, index, query plan, dan apa yang sebenarnya ingin dihitung.

Jangan mengoptimalkan berdasarkan asumsi. Ukur terlebih dahulu.

11. Gunakan SET NOCOUNT ON pada Stored Procedure

Untuk Stored Procedure yang melakukan banyak operasi, saya biasanya menggunakan: 

SET NOCOUNT ON;

Contohnya: 

CREATE PROCEDURE sp_ProcessEmployee
AS
BEGIN

    SET NOCOUNT ON;

    UPDATE Employee
    SET IsActive = 1
    WHERE IsActive = 0;

END

Ini membantu mengurangi pesan row count yang tidak diperlukan oleh aplikasi.

12. Jangan Menganggap Query yang Cepat Selalu Bagus

Ada query yang terlihat cepat ketika dijalankan sekali, tetapi menjadi masalah ketika dipanggil ribuan kali oleh aplikasi.

Misalnya sebuah query membutuhkan 50 ms. Jika dipanggil 10.000 kali, total waktunya menjadi sangat signifikan.

Karena itu performa harus dilihat dari konteks bagaimana query tersebut digunakan oleh aplikasi.

13. Blocking Bisa Membuat Query Terlihat Lambat

Tidak semua query lambat karena query-nya buruk. Bisa saja query sedang menunggu transaksi lain.

Salah satu hal yang perlu diperiksa ketika aplikasi tiba-tiba lambat adalah blocking. 

EXEC sp_who2;

Untuk troubleshooting yang lebih mendalam, DMV SQL Server juga sangat berguna untuk melihat session, request, blocking dan resource yang sedang digunakan.

14. Jangan Sembarangan Menggunakan NOLOCK

NOLOCK sering digunakan dengan alasan query menjadi lebih cepat. 

SELECT *
FROM Employee WITH (NOLOCK)

Tetapi NOLOCK bukan obat untuk semua masalah performa.

Dengan NOLOCK, query dapat membaca data yang belum committed atau mengalami fenomena pembacaan tertentu yang mungkin tidak sesuai dengan kebutuhan bisnis.

Kalau data yang dibaca berkaitan dengan laporan keuangan, payroll, inventory, atau proses bisnis penting, pahami konsekuensinya sebelum menggunakan NOLOCK.

15. Backup Itu Bukan Sekadar Formalitas

Salah satu pelajaran paling penting dalam database adalah:

Backup yang belum pernah diuji restore sebenarnya belum bisa dianggap sebagai backup yang benar-benar siap.

Backup harus memiliki strategi yang jelas dan, yang tidak kalah penting, proses restore harus pernah diuji.

Karena ketika database mengalami kerusakan, yang dibutuhkan bukan hanya file backup tetapi kemampuan untuk mengembalikan sistem.

16. DBCC CHECKDB untuk Pemeriksaan Database

SQL Server menyediakan DBCC CHECKDB untuk membantu memeriksa consistency database. 

DBCC CHECKDB ('DatabaseName')
WITH NO_INFOMSGS;

Ini sangat berguna sebagai bagian dari database maintenance dan troubleshooting ketika muncul indikasi corruption.

Jika ditemukan corruption, jangan langsung melakukan tindakan destructive tanpa memahami kondisi database dan backup yang tersedia.

17. SQL Server Lama Masih Banyak Digunakan

Salah satu hal menarik dalam dunia IT enterprise adalah bahwa teknologi tidak selalu mati ketika versi barunya muncul.

Saya masih menemukan aplikasi yang menggunakan teknologi lama seperti VB6 dan SQL Server versi lama.

Sistem tersebut mungkin sudah berumur bertahun-tahun, tetapi masih menjalankan proses bisnis penting.

Karena itu kemampuan memahami legacy system tetap memiliki nilai.

18. Jangan Takut dengan Database Besar

Database besar bukan otomatis berarti database buruk.

Yang penting adalah bagaimana data tersebut dikelola:

  • Index
  • Statistics
  • Query design
  • Partitioning jika memang diperlukan
  • Maintenance
  • Storage
  • Backup strategy
  • Monitoring

19. Ukur Sebelum Mengoptimalkan

Ini mungkin salah satu prinsip paling penting dalam performance tuning.

Measure first. Optimize second.

Jangan mengubah query hanya karena terlihat lebih pendek. Jangan menambahkan index hanya karena query terasa lambat. Jangan menggunakan NOLOCK hanya karena orang lain menggunakannya.

Cari data dan bukti terlebih dahulu.

20. SQL Server Bukan Hanya Tentang Query

Setelah bertahun-tahun bekerja dengan database, saya semakin melihat bahwa SQL Server bukan hanya tempat menyimpan data.

Database adalah bagian dari sebuah sistem yang lebih besar.

Ada aplikasi di sisi depan, business process, network, server, storage, user, dan tentu saja database.

Ketika terjadi masalah, semua bagian tersebut perlu dilihat sebagai satu kesatuan.

Kesimpulan

SQL Server adalah teknologi yang sangat luas. Tidak ada satu tips yang bisa menyelesaikan semua masalah performa database.

Pengalaman mengajarkan bahwa troubleshooting yang baik membutuhkan kombinasi antara pemahaman SQL, database, aplikasi, business process dan kemampuan membaca masalah secara sistematis.

Bagi saya, menjadi developer bukan hanya tentang membuat program berjalan.

Yang lebih penting adalah memahami mengapa program tersebut bekerja, bagaimana data diproses, dan bagaimana membuat sistem tetap dapat digunakan dengan baik dalam jangka panjang.

Catatan ini akan terus saya update seiring dengan pengalaman dan hal-hal baru yang saya temui.
